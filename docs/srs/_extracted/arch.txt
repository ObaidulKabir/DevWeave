1. Executive Summary and Architecture Outcomes
DevWeave is an AI Software Delivery Control Plane. It provides a persistent project knowledge model and coordinates 
software delivery performed by humans and multiple AI agents. It is not a source-code hosting platform and is not 
intended to replace coding environments, Git providers, CI/CD systems or model providers.
The platform has two execution modes under one common control plane: (1) customer-managed external agents 
operating on developer devices, customer servers or third-party runtimes; and (2) optional DevWeave-managed agents 
operating in isolated, metered workspaces. A single project and execution campaign may use both modes.
The architecture combines three interoperable interaction surfaces:
 MCP for agent-to-platform access to project knowledge, tools, resources and coordination capabilities.
 A2A for interoperable agent-to-agent messages, delegated tasks, status exchange and artifacts.
 DevWeave Coordination APIs and durable event infrastructure for authoritative plan, task, lease, policy, audit and 
integration state.
Core architectural rule
MCP and A2A are protocol interfaces, not sources of truth. The DevWeave domain services own canonical project, plan, 
campaign, task, lease, authorization, integration and history state.

DevWeave provides the project control plane around AI-assisted software development. It preserves the knowledge of

external code repositories, how the result was verified, and what was delivered.

2.3 Logical project boundary
A DevWeave Project represents a software initiative, product or bounded delivery effort. A project may contain one or 
more applications, services, repositories, databases, environments, delivery streams and execution campaigns. A project 
is owned by exactly one tenant in the initial ownership model. Cross-tenant collaborators may receive explicit grants; they 
do not change project ownership.
2.4 Same-codebase interpretation
Authoritative repository versus shared workspace
“Agents working on the same codebase” means agents contribute to the same authoritative repository set and target 
integration branch. It does not mean every agent writes concurrently into one shared working directory. Each active 
assignment uses an isolated branch, worktree, container or workspace, followed by controlled integration.
3. Scope, Assumptions and Constraints
3.1 In scope
 Multi-tenant SaaS control plane with tenant-owned projects and multiple applications/services per project.
 Universal project knowledge objects, type schemas, revisions, typed relationships, provenance, evidence and 
stakeholder views.
 Locked plan baselines and execution campaigns bound to a specific plan revision/hash.
 Agent identity, agent profile, runtime instance, capability discovery, admission and revocation.
 Project-scoped logical MCP service and A2A gateway/router with durable communication history.
 External/customer-managed agent connectors and optional DevWeave-managed execution workspaces.
 Dependency-aware scheduler, task ownership, leases, heartbeats, fencing tokens, retries and reassignment.\n\n===== PAGE 5 =====\n\nDEVWEAVE  |  ENGINEERING IMPLEMENTATION SPECIFICATION

5.2 Required architectural invariants
 A project has exactly one owning tenant; explicit collaborator grants are separately represented.
 Every canonical work item belongs to a project and, when executing, to an execution campaign bound to a plan 
baseline.
 Agent identity, runtime identity and human sponsor are distinct principals or linked identities.
 Only the Coordination Engine may grant, renew, revoke or expire canonical task/resource leases.
 Only the Integration Governance service may authorize a merge/integration transition.
 Protocol messages are untrusted input. They cannot change platform authority without a separately authorized 
domain command.
 A2A and MCP transport delivery is not treated as guaranteed delivery; durable records and replay are authoritative.
 Managed workspaces are ephemeral by default; persistent source code remains in the customer repository.\n\n===== PAGE 7 =====\n\nDEVWEAVE  |  ENGINEERING IMPLEMENTATION SPECIFICATION

6.1 Deployment boundary recommendation
Start as a modular .NET 10 solution with independently deployable edge/protocol hosts and worker processes where 
operational isolation is valuable. The business domains may initially run in one deployable API host, but must 
communicate through defined application contracts rather than direct cross-module table writes. Extract services only 
when scale, security isolation or independent release cadence justifies it.

8.1 Plan lock operation
1. All required planning objects and work packages are validated against their registered schemas.
2. Dependencies are validated for missing nodes, invalid cycles, contradictory scopes and unsatisfied prerequisites.
3. Repository baseline commit SHAs and target integration branches are captured for every connected repository.
4. The platform creates an immutable PlanBaseline with a canonical serialization and content hash (e.g. SHA-256).
5. Authorized owner(s) approve the baseline. Locking records approver, timestamp, scope, policy version and hash.
6. An ExecutionCampaign is created and bound to that plan baseline and its repository baseline commit(s).
Locked-plan invariant
An executing campaign MUST NOT silently mutate its baseline. Any material plan, requirement, interface or dependency 
change must create a change request, assess affected work, obtain required approval, and either create a new 
baseline/campaign or an explicitly approved campaign amendment with a complete before/after record.

8.3 Replanning and change control
A changed requirement does not automatically rewrite an in-flight assignment. The change service calculates impact over 
the knowledge/work-item graph: affected work packages, downstream dependencies, active leases, branches/PRs and 
verification rules. The owner may accept, reject or defer the change. Accepted changes create a new baseline or a 
versioned amendment; assignments derived from the superseded baseline are either explicitly grandfathered or 
invalidated.
9. Agent Identity, Registry and Capability Model
9.1 Registration and admission
 An agent must be registered at tenant scope and explicitly admitted into a project or campaign before receiving project 
context.
 The registry stores a stable logical agent identity independently from current runtime location.
 A runtime instance registers with an authenticated device/runner identity and binds to an approved agent registration.
 The registry stores protocol support: MCP client, A2A server/client, native provider API, or adapter-bridged support.
 Capabilities are declared and may be observed/verified; declared skill is not proof of quality or authorization.
 Agent registration can be suspended/revoked without deleting execution history.

9.3 Agent Card handling
For native A2A agents, the registry shall ingest and validate the A2A Agent Card. As of this document date, the A2A 
v1.0.0 well-known URI is /.well-known/agent-card.json. The platform shall cache cards according to declared cache policy 
and refresh them as required. A card is capability metadata, not an authorization credential. Private or extended Agent 
Card data must be authenticated and access-controlled. Where signatures are provided, the gateway should verify them; 
endpoints discovered from cards must pass outbound URL and SSRF controls.

10.3.2 A2A Task versus DevWeave Work Item
Do not conflate task models
A DevWeave WorkItem is the platform-owned unit of planned project work. An A2A Task is a protocol-level interaction/task at 
a remote agent. They are related through A2ATaskMapping and may have one-to-many relationships. A2A task completion 
does not automatically complete the DevWeave WorkItem; acceptance criteria and verification remain DevWeave decisions.
10.4 Agent-to-agent communication topology
Default mode is mediated communication. Agents do not need direct network connectivity or mutual trust. Agent A sends a 
request to the DevWeave A2A Gateway, which authenticates A, authorizes the project/campaign interaction, resolves 
Agent B through the registry, verifies B is eligible, routes the message/task and records the result. Direct agent-to-agent 
connectivity may be permitted only as an explicit enterprise policy and must preserve authorization and required audit 
metadata.
10.5 A2A is not a project-wide pub/sub bus
A2A standardizes agent interactions and task updates; it does not replace the platform's durable project event bus or a 
general multi-subscriber channel system. DevWeave shall maintain its own durable channel/message/event service for 
project-wide announcements, presence, task-state fan-out and event replay. A2A is used when an agent is the intended 
recipient of a peer interaction or delegated work.
11. Real-Time Coordination, Messaging and Event Delivery
11.1 Durable-before-notify flow
1. Validate sender identity and scope; apply tenant, project, campaign, channel, classification and recipient policy.
2. Validate payload against message type schema and source-code/secret content controls.
3. In one database transaction, persist the message/event, sequence/cursor, idempotency record and transactional 
outbox row.
4. Commit the transaction. Only then acknowledge durable acceptance to the sender.
5. Outbox dispatcher publishes a delivery event to the broker and marks dispatch state.
6. Delivery workers fan out to authorized subscribers and/or route A2A messages to recipient adapters.
7. Persist per-recipient delivery state, retries, expiry and terminal failure. Client reconnect uses cursor replay.
Delivery semantics
Design for at-least-once delivery with idempotent processing. Do not promise exactly-once transport. A channel sequence 
provides ordering within that channel only; no global ordering across a project is required.

 Agent/runtime availability, queue depth, concurrency slots and health.

12.2 Lease model
The Coordination Engine grants a lease for a WorkItem assignment. A lease includes lease_id, owner agent/runtime 
identity, issued_at, expires_at, heartbeat interval, fencing_token, plan_baseline_id, assignment_version and permitted 
scope. Lease writes use transactional compare-and-swap semantics in PostgreSQL. Redis may accelerate 
presence/cache but is not the lease authority.
Lease grant invariant:
  assignment.state = Assigned
  AND assignment.version = expected_version
  AND no unexpired exclusive lease exists for work item/resource
  => create lease with fencing_token = previous_token + 1
Every heartbeat/result mutation MUST present:
  lease_id + fencing_token + assignment_version
If token/version is stale or lease expired:
  reject with LeaseExpiredOrFenced; do not accept stale completion.

14. Shared-Codebase and Repository Integration
14.1 Repository baseline
A project can connect multiple repositories. A locked plan records the repository IDs, target integration branch and 
baseline commit SHA for each repository. Every campaign is bound to those baselines. Agents receive a scoped 
workspace derived from the correct repository baseline.
14.2 Branch/worktree policy
Recommended branch naming:
  dw/{campaign-key}/{work-item-key}/{agent-key}
Workspace policy:
  - One isolated workspace per active assignment by default.
  - No shared mutable worktree between independent agents.
  - Branch must start from the campaign's recorded baseline or an explicitly approved dependency artifact.
  - Agent must not push directly to protected target branch.
  - Commit SHA and PR/MR URL are recorded as external references only.
14.3 Integration queue
1. Agent submits execution result with commit/branch/PR reference and verification summary.
2. Repository adapter verifies repository identity, branch relationship, expected base commit and actor permissions.
3. CI/test/security checks execute in customer-controlled provider pipeline or approved execution environment.
4. Integration Governance evaluates required checks, dependency readiness, review policy, stale baseline and merge 
conflicts.
5. An authorized reviewer or policy-approved automation approves the integration request.
6. Repository provider performs merge; DevWeave records resulting merge commit SHA and evidence references.
7. Knowledge relationships and task state are updated only after successful provider confirmation and required 
verification.
14.4 Conflict handling
Merge conflicts, API contract conflicts, schema conflicts and failed integration checks must create explicit conflict records 
linked to affected assignments and work items. The integration queue must not select an arbitrary last-write-wins outcome. 
Rework can be assigned to the original agent or a designated integration agent under a fresh lease and current baseline.\n\n===== PAGE 19 =====\n\nDEVWEAVE  |  ENGINEERING IMPLEMENTATION SPECIFICATION

20.1 Backpressure and overload
The platform must enforce per-tenant and per-project quotas for concurrent assignments, message rates, subscriptions, 
runtime slots, artifact size and provider API requests. When capacity is exhausted, it should reject or queue with an explicit 
reason and retry hint; it must not silently drop durable coordination events.
20.2 Disaster recovery
Define RPO/RTO by deployment tier during production readiness. At minimum, use automated PostgreSQL backups and 
WAL/PITR, object-storage versioning/lifecycle protection, broker stream backup/configuration recovery, tested secret-store 
recovery, IaC-based environment reconstruction and periodic restore drills. Event and message retention must be 
consistent with legal, tenant and billing/audit obligations.

21.2 Module dependency rules

 Nullable reference types enabled; explicit validation and structured error handling.
 All state mutations use transactional boundaries and optimistic concurrency where relevant.

 No secrets or sensitive payloads in source control, logs or test snapshots.
 Database migrations are reviewed and tested against production-like datasets.
 Every new event/tool/API has owner, authorization rule, schema version and tests.
 Every new agent/provider adapter has capability declaration, conformance tests, failure modes and support policy.

23.2 Mandatory end-to-end acceptance scenarios

Engineering Conclusion
DevWeave should be implemented as a knowledge-first, protocol-interoperable software delivery control plane. The core 
platform owns project knowledge, approved plan baselines, campaign/task authority, leases, agent registry, durable 
coordination events and integration governance. MCP gives agents a standard way to use DevWeave capabilities; A2A 
enables interoperable agent collaboration. Durable project messaging and event infrastructure preserve state and replay 
across disconnections. External and managed runtimes remain replaceable adapters under one common policy model.\n\n===== PAGE 33 =====\n\nDEVWEAVE  |  ENGINEERING IMPLEMENTATION SPECIFICATION

Implementation sequencing guardrails
 Freeze and version canonical domain, event, REST, MCP and A2A contracts before expanding provider adapters.
 Establish tenant identity, project authorization, agent admission and audit controls before enabling inter-agent 
communication.
 Deliver durable messaging, idempotency, task leases and fencing before sophisticated autonomous scheduling.
 Prove customer-managed runners and repository integration before introducing DevWeave-managed execution at 
scale.
 Keep source code in customer-controlled repositories; persist only approved metadata, references, evidence and
