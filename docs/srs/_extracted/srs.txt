1. Introduction
1.1 Purpose
This Software Requirements Specification (SRS) defines the business-aligned product, functional, information, interface, 
security, quality, operational, commercial-platform and extensibility requirements for DevWeave. It is the shared baseline for 
product planning, architecture, implementation, procurement, verification, release decisions and future change control. It 
distinguishes product capabilities and measurable business outcomes from non-binding market, pricing and revenue 
hypotheses.
DevWeave is an AI Software Delivery Control Plane for organizations that plan, coordinate and verify software development 
performed by humans and AI agents. It combines a persistent project-knowledge system with a project-scoped, real-time agent 
coordination service. It allows multiple agents operating across providers, devices, locations and runtime environments to 
execute an approved plan against one authoritative external codebase through isolated workspaces and governed integration. 
Customers may connect externally operated agents and, optionally, use DevWeave-managed execution environments. The 
canonical knowledge store is not a source-code repository: managed runtimes may temporarily materialize source code in 
isolated, ephemeral workspaces, but source code shall not be retained as project knowledge or permanent platform content.
1.2 Product vision
Product vision / DevWeave shall enable software organizations—initially AI-first software development agencies and AI-native 
studios—to turn approved software plans into coordinated, evidence-backed delivery across multiple AI agents and execution 
environments. It shall preserve the project knowledge and decision history, coordinate external agents through a project-level MCP 
service, provide optional managed execution, and expose trustworthy progress and delivery evidence to authorized owners, clients, 
reviewers and other stakeholders. Its long-term direction is to serve as an agent-neutral control plane across software projects, 
coding tools, repositories and execution providers.
1.3 Scope
The system shall provide a shared, extensible SaaS foundation on which each tenant can create and manage multiple software-
development projects. Each project may represent a product, system, application suite, platform or software initiative and may 
reference multiple repositories, services, deployment environments, agent providers and external tools. Each project shall have 
a logical project-scoped MCP service identity and resource namespace for authorized real-time agent coordination. The platform 
shall support customer-managed external agent execution as the initial commercial mode and optional DevWeave-managed 
execution as a later, separately metered mode. Both modes shall use the same canonical project knowledge, coordination, 
governance and evidence services.
1.3.1 In scope
 Multi-tenant identity, membership, project ownership, project-scoped access grants and tenant application installations.
 A universal knowledge-object model with registered types, versioned schemas, metadata, revisions, typed relationships and 
provenance.
 Lifecycle and execution records for planning, design, AI/human activities, verification, release, deployment, operation and 
evolution.
 Documents, diagrams, charts, structured artifacts, evidence and external references, subject to content policy and retention 
settings.
 AI-agent identity, authorization, context retrieval, activity reporting, output registration, evidence submission and 
review/approval.
 Stakeholder-specific dashboards, reports, search and learning/user views over a common canonical model.
 Integrations with source-code hosts, coding agents, CI/CD, testing, deployment, identity and other external systems, 
primarily through metadata and references. Distributed agent coordination, work-package scheduling, workspace/branch 
references, task/resource leases and merge/integration governance.
 Export, audit, schema evolution, operational monitoring and future application/extension capabilities.
1.3.2 Out of scope
 Permanent source-code hosting, source-code repository replacement, or retention of source files, diffs, patches, executable 
snippets or raw code-bearing transcripts in the canonical knowledge store. Optional DevWeave-managed execution may 
temporarily materialize source code in isolated, short-lived workspaces solely to perform authorized tasks; those 
workspaces are execution infrastructure, not project knowledge storage, and shall follow controlled cleanup and retention 
policies.\n\n===== PAGE 6 =====\n\nDEVWEAVE  |  SOFTWARE REQUIREMENTS SPECIFICATION

 Replacing Git hosting, IDEs, build systems, container registries, test execution platforms, deployment platforms or 
production observability tools.
 A general-purpose workflow automation engine unrelated to software-project knowledge and lifecycle records.

 Autonomous production deployment by default; this may be integrated later under separately approved controls.

1.4 Intended audience
The SRS is intended for the product owner, business analyst, software architect, engineering lead, backend/frontend 
developers, AI integration engineers, data engineer, security/privacy reviewer, QA team, DevOps/SRE team, tenant 
administrators and project stakeholders who approve scope and acceptance.
1.5 Product boundary
DevWeave is the system of record for project knowledge objects, approved revisions, relationships, activities, provenance, 
evidence metadata, stakeholder access policies, coordination state and external references. External code hosts remain 
authoritative for repository history and source code. External customer-managed agents or optional DevWeave-managed 
runners perform code changes in isolated workspaces; DevWeave records task contracts, runtime metadata, workspace 
references, commit/branch/PR references, outcomes and evidence. Source code may exist transiently inside an authorized 
managed execution workspace, but shall not be ingested into the canonical knowledge store, search/vector indexes, event 
payloads, analytics or durable audit records.
1.6 Requirement language and priority
The key words SHALL, SHALL NOT, SHOULD, SHOULD NOT and MAY are normative. Priority codes: M (Must), S (Should), C 
(Could). Release tags are MVP (technical foundation), R1 (first commercial pilot/launch), R2 (hybrid managed execution and 
commercial scale) and R3/FUT (enterprise and advanced future capabilities). MVP establishes the platform foundation; R1 is 
the first customer-facing product release and includes the agent-coordination wedge.
1.7 Standards and reference guidance
This SRS draws on ISO/IEC/IEEE 29148 and 15289 for requirements and lifecycle information, ISO/IEC 25010 for product 
quality, W3C PROV-O for provenance, JSON Schema for payload validation, NIST SP 800-162 for attribute-based 
authorization, and OWASP ASVS for application security verification. These references do not imply certification. Status shall be 
rechecked at each major baseline approval.
2. Overall Product Description
2.1 Product perspective
DevWeave is a hybrid AI software-delivery control plane composed of a canonical Knowledge Plane, a Coordination/Control 
Plane and one or more Execution Plane providers. Owner Studio, Agent Workspace, agency/client views, investor/reviewer 
views, learning/user experiences, administration and future applications shall consume the same canonical project information 
services. The Coordination Plane manages project-scoped MCP collaboration, execution campaigns, work-package 
assignments, runtime sessions, resource leases, usage/entitlement checks and integration queues. The Execution Plane may 
consist of customer-managed external runtimes, DevWeave-managed ephemeral runners, or both in one campaign. External 
repositories remain authoritative for source code.

2.5 Operating environment
 Web apps shall support current stable major evergreen desktop browsers; core reading/review flows shall be responsive on 
mobile.
 Backend services shall be deployable as containerized workloads in a cloud or customer-approved hosting environment.
 Initial reference stack: ASP.NET Core on a supported .NET LTS release, EF Core, PostgreSQL, S3-compatible object 
storage and Next.js/TypeScript. These are implementation baselines, not domain dependencies.
 Domain services shall remain protocol-neutral. Each project shall expose a logical project-scoped MCP coordination service 
as the standard real-time collaboration interface for MCP-capable agents. REST/OpenAPI and authenticated runtime 
adapters shall remain available for applications, administration, integrations and agents whose native runtime does not 
implement MCP; an adapter or local worker may bridge such agents to the project coordination service.
 The platform shall tolerate external-system outages and expose integration delivery status rather than silently dropping 
events.
2.6 Design and implementation constraints
 Each project shall have one owning tenant; cross-tenant participation shall be explicit, revocable and auditable.
 Tenant isolation shall be enforced at application, database and storage boundaries; application checks alone are 
insufficient.
 The primary data model shall work without a graph database; typed relationships may be relationally stored and indexed.
 Full event sourcing shall not be required for every aggregate; use current-state records, immutable knowledge revisions and 
append-only events where appropriate.
 Knowledge schemas and relationship types shall be registered and versioned; tenant extensions cannot redefine reserved 
platform types.
 AI-generated statements shall not automatically become approved or verified facts.
 No application interface shall bypass canonical domain authorization and validation.

3. Product Architecture and Design Constraints
3.1 Recommended implementation architecture
The initial implementation shall use a modular monolith with explicit module boundaries and independently scalable background 
workers. Knowledge, coordination, commercial entitlements and execution-provider integration shall be separately bounded 
domains. The architecture shall distinguish control-plane responsibilities from execution-plane responsibilities and permit later 
extraction of bounded modules/services without changing public domain identifiers or creating application-specific copies of 
project data.

3.2 Architectural principles
 Knowledge before documents: files are representations/payloads attached to typed knowledge identities.
 One canonical model: applications derive views from shared services and do not create conflicting copies.
 History before overwrite: important changes create new revisions or immutable events.
 Evidence before claims: reported completion, verification and approval remain distinct.\n\n===== PAGE 10 =====\n\nDEVWEAVE  |  SOFTWARE REQUIREMENTS SPECIFICATION
Page 10 of 75
 Authorization before retrieval: permissions precede search, summaries, embeddings, analytics and AI context.
 Extensibility without semantic chaos: custom types/workflows require schemas, versions, ownership and validation.
 Hybrid execution boundary: external/customer-managed and optional DevWeave-managed runtimes perform code work in 
isolated workspaces; external code hosts remain authoritative, and the canonical knowledge store preserves metadata, 
references, outcomes and evidence rather than source-code payloads.
 Portable knowledge: exports include identifiers, schemas, revisions, relationships and provenance.
3.3 Technical baseline and version policy
At the SRS date (09 November 2026), .NET 10 is the recommended LTS baseline. Re-evaluate at implementation kickoff and 
each major release; use a vendor-supported release with current security patches. PostgreSQL 18 is the preferred initial 
database, JSON Schema Draft 2020-12 the default payload dialect, and OpenAPI 3.2.1 the preferred HTTP API description 
baseline where tooling is compatible. Pin versions in the implementation bill of materials and review at least quarterly.
The domain model shall not depend on .NET, PostgreSQL, JSON Schema, OpenAPI or MCP-specific types; adapters shall 
isolate these technology choices.

4.2 Representative agent-assisted delivery flow
1. Owner records approved goals, requirements, constraints, decisions and work items.
2. Owner assigns a work item to an agent principal with task-scoped permissions.
3. Agent requests context; platform captures a snapshot with exact revision references.\n\n===== PAGE 12 =====\n\nDEVWEAVE  |  SOFTWARE REQUIREMENTS SPECIFICATION
Page 12 of 75
4. Agent works in an external coding environment; source code remains in the external repository. For coordinated 
campaigns, the platform dispatches plan-bound work packages to eligible agent runtime instances; each writer operates in 
an isolated workspace or branch against a recorded repository baseline.
5. Agent submits execution summary, proposals, repository/commit/PR refs, test-run refs and outcome. The Coordination 
Plane tracks lease ownership, dependencies, heartbeats, change-set references, integration gates and the campaign-level 
goal across all participating agents.
6. Platform validates submission, applies content policy and records provenance; unverified claims remain unverified.
7. Reviewer evaluates evidence and records approval, rejection or corrective action.
8. Stakeholder views refresh from canonical information and show evidence/freshness.

5.1 User interfaces
 UI-01: Owner Studio shall provide project overview, settings, knowledge browser, relationship explorer, revision history, 
activity timeline, evidence review and access management.
 UI-02: Project-scoped screens shall identify the current tenant and project context.
 UI-03: The interface shall distinguish draft, proposed, approved, rejected, verified, failed, superseded and obsolete 
information.
 UI-04: Important displayed information shall show source, revision, last-updated time and verification status.

layouts.
 UI-06: Approval, revocation, export, deletion/retention change and integration authorization shall require explicit 
confirmation and audit.
 UI-07: Hiding a UI control shall not be treated as authorization; APIs shall enforce the same policies.
5.2 API interfaces
 API-01: The platform shall expose a versioned HTTPS API described by machine-readable OpenAPI.
 API-02: Responses shall use stable IDs, explicit schema versions, UTC timestamps and documented error semantics.
 API-03: List endpoints shall use bounded pagination and deterministic ordering; large traversals shall use cursor pagination.
 API-04: Mutating operations shall support idempotency keys where retries could create duplicates.
 API-05: Revision writes shall use optimistic concurrency (e.g., ETag/If-Match or expected revision).
 API-06: Tenant clients and agents shall not receive direct database or unrestricted query-language access.
 API-07: Backward-incompatible API changes shall require a new major version and published migration/deprecation policy.
5.3 Agent interfaces
 AGI-01: Agent access shall use a machine principal with revocable credentials and explicit scopes.
 AGI-02: Agent operations shall use protocol-neutral domain services. The platform shall provide a project-scoped MCP 
service as the standard and mandatory interface for real-time agent-to-agent coordination; REST/OpenAPI shall remain 
available for application, administration, integration and non-MCP use cases.
 AGI-03: Tool schemas shall describe validation, permissions, side effects, idempotency, errors and output references.
 AGI-04: Agents shall not receive unrestricted tenant search, approval authority or cross-project access by default.
 AGI-05: Context responses shall include item/revision IDs, scope, context snapshot ID and freshness metadata.\n\n===== PAGE 13 =====\n\nDEVWEAVE  |  SOFTWARE REQUIREMENTS SPECIFICATION
Page 13 of 75
 AGI-06: Each project shall have a logically project-scoped MCP service identity, endpoint/resource namespace and policy 
configuration. Shared infrastructure may host many logical project services; a dedicated process per project is not required.
 AGI-07: The project MCP service shall expose authorized coordination tools and resources for agent discovery, presence, 
channels, messages, handoffs, coordination state and event replay.
 AGI-08: Authorized agent clients shall be able to subscribe to project/campaign/channel resource changes and retrieve 
durable messages/events by cursor after notification or reconnect.
 AGI-09: The platform shall mediate agent-to-agent collaboration. Agents shall not need direct network connectivity or direct 
trust relationships with one another.
 AGI-10: MCP transport notifications shall be treated as best-effort wake-up signals; durable message/event records and 
cursor-based replay shall be authoritative.

 Every project shall have exactly one owning tenant; project identity is independent of display name or project key.

7.3 Revision and temporal rules
 Each KnowledgeItem shall have a stable identity and zero or more immutable revisions; a current-revision pointer identifies 
the selected revision.
 Revisions shall preserve the schema version under which the payload was validated.
 The system shall distinguish recorded/transaction time from valid/effective time where backdated corrections or imported 
history are supported.
 Corrections shall create a new revision or controlled redaction/tombstone event; silent overwrite is prohibited for governed 
content.
 Ordinary application roles cannot update/delete immutable revisions or events. Exceptional retention/legal deletion uses 
controlled privileged workflows with audit evidence.

structured execution metadata may be retained.

10. Security, Privacy and AI Governance
10.1 Security model
The platform shall use defense-in-depth authorization combining role-based access control (RBAC), 
resource/subject/action/context attributes (ABAC), and relationship-based project membership or sharing. Tenant membership 
alone shall not grant access to every project or object.
10.2 Mandatory security controls
 Authentication shall use a standards-based identity provider where practical. Service/agent credentials shall be scoped, 
rotated, revocable and stored in a protected credential store.
 Authorization shall be server-side and deny by default. Tenant context shall derive from verified identity and membership, 
not a client-supplied tenant ID.
 The relational store should use row-level security as defense in depth. App roles shall not have superuser/BYPASSRLS; 
table-owner bypass shall be considered and FORCE ROW LEVEL SECURITY applied where appropriate.
 Object storage shall use private buckets/containers, tenant-aware object keys, mediated authorization, short-lived signed 
access and encryption at rest.
 Caches, search documents, vector records, background jobs and event subscribers shall preserve tenant scope; sensitive 
delivery shall recheck authorization.
 State-changing security actions shall create audit records. Audit data shall not contain credentials, prohibited code or 
unnecessary personal data.\n\n===== PAGE 32 =====\n\nDEVWEAVE  |  SOFTWARE REQUIREMENTS SPECIFICATION
Page 32 of 75
 Web application security verification shall use OWASP ASVS 5.0.0 as baseline; the security lead shall select target 
verification level and applicable controls.
 Production secrets shall be managed separately from application configuration and shall not be committed or embedded in 
images.
10.3 Privacy and tenant data control
 The product shall maintain a data inventory with personal-data categories, purpose, source, storage location, recipients, 
retention and deletion method.
 Tenants shall be able to configure permitted retention and external AI processing policies within platform/legal constraints.

 The system shall support export, correction, deletion/anonymization and legal hold consistent with applicable law and

 Data residency, cross-border transfer, subprocessors and processing terms shall be decided before production onboarding

12. Deployment, Operations and Support
12.1 Deployment model
 Initial deployment comprises containerized web/API instances, background workers, PostgreSQL, private object storage

 Production, staging, test and development environments shall be isolated. Production data shall not be copied to lower

The production runbook shall define backup scope/frequency for relational data, object metadata/binaries, schema registry,

 Support staff shall use approved time-limited grants to inspect tenant data; access shall identify reason/ticket and be 
recorded.
 Tenants shall be able to request machine-readable export of their data and permitted binaries.
 Tenant closure shall disable access, revoke credentials/integrations, apply retention/legal holds and delete after approved 
retention period.
 Before general availability, platform support shall publish status, incident communications and security contact procedures.

16. Amendment 1.1 — Multi-Agent Distributed Execution and Shared-
Codebase Coordination
This section is a normative coordination specification within the DevWeave SRS. It makes plan-locked multi-agent coordination 
over shared external codebases a first commercial-release capability (R1). It shall be read together with Sections 1–15 and the 
business-aligned release strategy in Section 18. Where an earlier statement or release table places core project MCP 
coordination and customer-managed distributed execution in R2, Section 18 and this release alignment take precedence. 
Optional DevWeave-managed execution is an R2 capability. Permanent source-code hosting or repository replacement remains 
out of scope.
16.1 Purpose and scope
The platform shall coordinate multiple authorized AI agents, potentially operating from different physical locations, devices, 
operating systems, containers or hosted runners, to implement one approved plan against the same authoritative external 
codebase or defined set of codebases. The agents shall work toward one campaign objective, share a consistent plan baseline 
and coordinate dependencies, work ownership, resource conflicts, workspace isolation, change submission, verification and 
integration.
The platform is the coordination control plane, not the source-code data plane. Source code remains in the external repository 
and execution workspaces. The platform stores task instructions and approved non-code context, repository and commit 
identifiers, branch/workspace references, lease state, changed-path metadata where permitted, pull/merge-request references, 
CI/test identifiers, status, sanitized summaries and evidence metadata. It shall not store source files, patch bodies, diffs, 
executable code snippets or raw code-bearing transcripts.
“Same codebase” means that participating work packages target the same registered authoritative repository identity and 
campaign integration target (or an explicitly declared set of repositories). It does not mean that agents are permitted to write 
concurrently into one shared local working directory. Concurrent implementation shall use isolated workspaces/branches or 
explicitly partitioned scopes, followed by controlled integration.

16.3 Coordination architecture and responsibilities
The Coordination Plane shall be a bounded domain module in the initial modular monolith. It may later be extracted into 
independently scalable services without changing its public domain contracts. It shall include the following logical capabilities:
 Execution Campaign Manager: creates campaigns from locked plan baselines, binds common goals and repository targets, 
and manages campaign lifecycle.
 Agent Registry and Runtime Session Manager: registers agent principals and runtime instances, records declared 
capabilities and availability, authenticates sessions, tracks heartbeats and supports revocation.
 Participation and Scheduling Service: receives agent offers, evaluates eligibility and capability fit, and dispatches authorized 
work packages.
 Work Package and Dependency Manager: converts or maps approved plans into implementable work packages, maintains 
dependency DAGs, scope boundaries and acceptance criteria.
 Lease and Resource Coordination Service: grants, renews, expires and revokes task/resource leases; prevents conflicting 
active writers for exclusive scopes.
 Workspace/Repository Adapter: requests or records isolated branches/workspaces through external providers and binds 
them to base commits and campaign targets.
 Integration Coordinator: evaluates change-set references, CI/test signals, approvals and merge policies; serializes 
integration into protected target branches.
 Campaign Telemetry and Recovery: aggregates status, failures, disconnects, blockers, reassignments and goal-level 
evidence; supports pause/resume/recovery.
The platform shall not require all agents to run on platform-hosted compute. Remote agent runtimes shall connect through 
authenticated outbound connections or supported provider APIs. The platform shall not assume shared local storage, stable IP 
addresses, a single operating system or a permanently connected device.
16.4 Operating model and lifecycle
The standard coordinated execution flow shall be:
1. Complete planning: the project owner and authorized reviewers approve goals, requirements, architecture, constraints, work 
dependencies, acceptance criteria and applicable policies.
2. Lock plan: an authorized actor locks the plan. The platform creates an immutable PlanBaseline referencing exact 
KnowledgeItem revisions, relationship versions, lifecycle profile version and success criteria.
3. Register codebase targets: the owner links the campaign to the external repository or repositories, protected target branch 
and starting commit SHA. The integration policy is recorded.
4. Create campaign: the platform creates an ExecutionCampaign bound to the PlanBaseline and CodebaseTargets. No work 
package may execute against an unbound or ambiguous baseline.
5. Mobilize agents: authorized agents/runtimes discover eligible campaigns or receive invitations, register 
capabilities/availability and submit ParticipationOffers. The owner or policy engine authorizes participation.
6. Prepare work packages: plan items are decomposed or mapped into work packages with explicit scope, objective, 
dependencies, allowed resources/paths, constraints and acceptance criteria.
7. Assign and lease: the scheduler assigns eligible work packages; the Lease Service issues short-lived task/resource leases 
and a context snapshot pinned to the plan baseline.
8. Execute remotely: each writing runtime uses an isolated workspace/branch based on the recorded repository commit. Agents 
report start, heartbeat, progress, checkpoints, blockers and results.
9. Submit change sets: an agent submits external commit/branch/PR/MR references and permitted metadata. The platform 
records provenance and links outputs to the work package and campaign.
10. Verify and integrate: configured checks, review and approvals run. Eligible changes enter a serialized integration queue and 
are merged into the authoritative target branch only through policy.
11. Update campaign state: the merged commit SHA, test evidence and accepted work-package state update the campaign 
projection. The overall goal is complete only when campaign acceptance criteria are met.
12. Close or evolve: campaign completion, cancellation or supersession is recorded. A changed plan is handled through change 
control and a new baseline or explicitly approved migration of the campaign.\n\n===== PAGE 47 =====\n\nDEVWEAVE  |  SOFTWARE REQUIREMENTS SPECIFICATION

16.6.3 Business invariants
 MCO-BR-01: Every ExecutionCampaign references one immutable PlanBaseline; all execution records identify the baseline 
used.
 MCO-BR-02: A campaign target identifies an external repository and integration branch; source code remains authoritative 
in that external provider.
 MCO-BR-03: An agent principal may have multiple runtime instances, but each runtime session is independently 
authenticated, scoped and revocable.
 MCO-BR-04: A ParticipationOffer is not a grant. No task or repository access is given until campaign authorization and 
assignment succeed.
 MCO-BR-05: One exclusive work package/resource has at most one active write lease. Partitioned concurrent writers must 
have validated non-overlapping scopes.
 MCO-BR-06: A lease is time-bounded and fenced. An expired or revoked runtime cannot commit a valid coordination state 
transition using an old lease.
 MCO-BR-07: Concurrent writers use separate workspaces/branches or an explicitly approved partitioned/shared-session 
protocol; no assumption of a shared filesystem is permitted.
 MCO-BR-08: Protected target branches are updated only through the repository policy and IntegrationQueue when the 
campaign requires controlled integration.
 MCO-BR-09: Submitted, reviewed, tested, merged and verified are separate states; agent self-report does not establish 
integration or goal completion.
 MCO-BR-10: A change to the locked plan creates a change record and, when approved, a new baseline or controlled 
migration; historical work retains its original baseline reference.
 MCO-BR-11: Multi-location operation shall not rely on trusted network location; identity, session security and authorization 
are required for every runtime.
 MCO-BR-12: Coordination events and provider notifications are processed idempotently; retries must not duplicate 
assignments, merges or accepted outputs.
 MCO-BR-13: A code-host outage or unavailable runtime may pause or block progress but shall not cause the platform to 
report success.
 MCO-BR-14: Platform telemetry shall not capture source-code content, patch bodies, secrets or raw code-bearing 
transcripts.

16.9 Security, privacy and source-code boundary
 Runtime authentication shall be based on machine identity and short-lived session credentials. Credentials shall be 
revocable independently of the durable Agent Principal.
 A task lease is an authorization-bound coordination token, not a substitute for repository-provider authorization. External 
code-host tokens shall be least-privilege and limited to the required repository/branch/actions.
 A local laptop or remote device shall not be trusted merely because it is in a known network or geographic location. Device 
posture/attestation may be added by policy but shall be an explicit capability.
 The platform shall not transmit an agent a repository credential broader than the campaign target and task require. Where 
possible, repository operations shall be mediated by a scoped integration service or short-lived provider credential.
 Runtime logs and telemetry shall capture operational facts (session, task, timing, result, error category) without source-code 
bodies, secrets, access tokens or full prompts containing restricted/code data.
 Agent participation is opt-in/authorized per campaign. Agent registration alone does not imply permission to inspect a 
project, join a campaign, access a repository or execute a task.
 A human approver shall be configurable for plan lock, re-baselining, protected-branch integration and production-impacting 
actions. Autonomous approval shall be explicitly enabled, narrowly scoped and audited if ever supported.

16.14 Normative conclusion
The platform shall support coordinated, distributed, multi-agent implementation as a first-class capability. Multiple authorized 
agents may work from different locations and devices toward one shared goal and one authoritative external codebase after 
planning has been locked. Safe parallelism is achieved through plan-bound work packages, capability-aware assignment, 
authenticated runtime sessions, leases/resource reservations, isolated workspaces/branches, dependency management and 
controlled integration—not by allowing uncoordinated concurrent writes to the same working directory. The Coordination Plane 
shall preserve the complete execution and integration history while maintaining the strict source-code exclusion boundary. Each 
project shall provide a project-scoped MCP coordination service through which authorized agents can discover participants, 
exchange durable messages, negotiate work, subscribe to coordination changes and recover missed events. The service shall 
mediate communication; it shall not depend on direct agent-to-agent connectivity.

17. Project-Level MCP Service and Real-Time Agent-to-Agent 
Coordination
17.1 Purpose and requirement status
This section adds a mandatory coordination capability to DevWeave. In addition to preserving project knowledge and 
coordinating distributed implementation work packages, the platform shall provide a logically project-scoped Model Context 
Protocol (MCP) service that enables authenticated agent runtimes participating in the same project or execution campaign to 
communicate and coordinate with one another in real time.
The service is a platform-mediated coordination mechanism. Agent A submits a message or coordination action to the project 
MCP service; the service authorizes and durably records the action; subscribed Agent B clients receive a change notification 
and retrieve the corresponding event/message. Agents do not need direct network reachability, shared filesystems or direct trust 
relationships.
The MCP interface is mandatory for standardized real-time agent-to-agent collaboration. REST/OpenAPI remains available for 
user applications, administrative operations, integrations, reporting and non-MCP clients. MCP tools shall call canonical domain 
services; they shall not create a second source of truth.
Priority: M / R1 for delivery of the first commercial coordinated-agent collaboration capability. A logical project-scoped MCP 
service identity, endpoint reference, resource namespace and policy record shall exist for every project from the project model; 
real-time coordination capabilities are delivered in R1. The implementation may host many logical project services on a shared, 
horizontally scaled service fleet; a dedicated process or server deployment for every project is not required.

17.3 Service boundary and deployment model
 The platform shall provision or make available a logical MCP service identity and resource namespace for each project. The 
service may be disabled only by an explicit tenant/project policy; disabling it shall not delete historical coordination records.
 A shared MCP service fleet may serve multiple tenants and projects. Every request shall identify the project context 
explicitly or derive it from a verified opaque endpoint plus the authenticated grant. The service shall not rely on connection 
affinity to infer the project, agent, campaign or conversation.
 The service shall integrate with the canonical Identity, Tenancy, Project, Agent, Coordination, Governance, Provenance and 
Audit modules. It shall not connect directly to PostgreSQL from third-party agents and shall not expose arbitrary SQL, 
filesystem access or unrestricted repository operations.
 Project configuration shall control the enabled coordination capabilities, channel types, allowed agent classes, message 
schemas, retention rules, subscription policies, rate limits and integration capabilities.\n\n===== PAGE 58 =====\n\nDEVWEAVE  |  SOFTWARE REQUIREMENTS SPECIFICATION

17.9 Payload schema and source-code boundary
 Coordination message payloads shall use registered, versioned schemas. The default message body shall support concise 
text and structured metadata, with references to existing KnowledgeItems, WorkPackages, Evidence, Activities or external 
resources.
 Binary content shall be sent as an authorized artifact reference, not embedded as an unrestricted binary payload. Artifact 
scanning, classification and source-code exclusion policies shall apply.
 Source files, patch bodies, code diffs, executable payloads, credentials, secrets and raw code-bearing prompts/transcripts 
shall not be preserved in coordination messages or event payloads. The ingestion path shall reject, redact or quarantine 
detected prohibited content before persistence.
 Coordination messages from other agents are untrusted data. Agents and hosts shall not interpret a message as a system 
instruction, approval, policy override or authorization grant. Each recipient runtime remains responsible for safe prompt 
construction and tool gating.
 The sender identity used for authorization shall be obtained from validated credentials or trusted runtime attestation, not 
from a message body or self-reported MCP clientInfo field.\n\n===== PAGE 63 =====\n\nDEVWEAVE  |  SOFTWARE REQUIREMENTS SPECIFICATION

17.10 Delivery, ordering, presence and recovery semantics
Concern Normative semantics
Persistence A successful send result means the message and its event/outbox record are 
durably committed. It does not mean any recipient has received or read it.
Ordering The service shall allocate a monotonically increasing sequence per channel. It 
shall not promise a single total order across independent channels.
Notification
MCP resource-update notifications are best-effort signals. They may be 
delayed, duplicated or missed across disconnects. They shall not be the only 
copy of the content.
Read/replay
A client shall retrieve messages/events using the channel resource and a last-
seen cursor. Reconnect shall replay from the last successfully processed 
cursor.
Delivery model
The platform shall provide at-least-once availability through durable replay; 
clients shall deduplicate by event/message ID and idempotently process 
updates. Exactly-once network delivery shall not be claimed.
Acknowledgement Read and acknowledgement are explicit and separate from notification 
dispatch. A consumer may record a processed-through cursor.
Presence Presence is approximate. The platform shall report last heartbeat and 
freshness rather than assert continuous human/agent attention.
Handoff
Handoff follows propose → accept/reject → authoritative assignment/lease 
transition. Timeout or rejection leaves ownership unchanged unless a recovery 
policy explicitly reassigns it.
Backpressure
Slow subscribers shall not block message persistence or unrelated tenants. 
The service shall bound queues, signal lag, and rely on replay rather than 
unbounded in-memory buffering.
Recovery Outbox/event dispatch, subscription reconnect, runtime rejoin and service 
restart shall preserve durable records and allow cursor recovery.
17.11 Protocol conformance and compatibility
The SRS protocol baseline is the published MCP specification dated 2026-07-28 as reviewed on 09 November 2026. 
Implementation shall re-check the official specification and SDK support at engineering kickoff; this version reference is a 
baseline, not permission to implement draft protocol behaviour.
 The service shall conform to the negotiated MCP protocol version and advertise the capabilities it actually implements. It 
shall not expose undocumented custom JSON-RPC methods as if they were standard MCP methods.
 For the 2026-07-28 protocol profile, requests are stateless. Every request shall carry required protocol metadata and 
explicit application handles. The server shall not infer project, campaign, message or conversation continuity from a TCP 
connection, HTTP connection, process or previous request.
 The service shall use the standard MCP tools/resources model. For resource-change updates it shall support the protocol-
defined subscriptions/listen mechanism and resourceSubscriptions filter where negotiated. A resource update notification 
signals that the resource changed; the client then reads the current resource or event page.
 The 2026-07-28 MCP specification does not make notifications a durable event log. DevWeave shall therefore maintain 
durable message/event records and cursor-based replay independently of the notification stream.
 The service shall not rely on deprecated legacy HTTP+SSE or session assumptions for a new implementation. 
Compatibility with earlier supported agents shall be implemented through explicit, tested adapters or version negotiation, 
not silent protocol ambiguity.
 Authentication and authorization shall follow the applicable MCP HTTP authorization requirements and DevWeave identity 
policies. Self-reported clientInfo/serverInfo fields may be used for diagnostics but shall not be treated as authenticated 
identity.

 Project administrators shall be able to define allowed channel types, recipient classes, retention periods, message

 The platform shall provide controls to report, mute, block or remove an abusive participant and to preserve relevant audit

17.15 Business rules and invariants
 MCP-BR-01: Every logical project MCP service is bound to exactly one project scope and one owning tenant.
 MCP-BR-02: Agent identity is established by trusted authentication; self-reported MCP client metadata is not an 
authorization credential.
 MCP-BR-03: A message is not accepted until its durable record and event/outbox record have committed.
 MCP-BR-04: Channel order is authoritative within a channel only; no global ordering guarantee is made across all 
project events.
 MCP-BR-05: Notifications are hints. Durable messages/events plus cursors are the source of truth.
 MCP-BR-06: A disconnected agent may miss notifications but shall be able to recover retained events from its 
cursor.
 MCP-BR-07: Agent-to-agent communication is mediated by the project service; direct agent connectivity is never 
assumed.
 MCP-BR-08: Messages do not confer authority. Task assignment, lease, approval, plan changes and repository 
integration remain governed by their canonical services.
 MCP-BR-09: Presence is approximate and expires. It is not a guarantee that an agent is actively reasoning, available 
for work or safe to assign.
 MCP-BR-10: Every resource and message is subject to tenant, project, campaign, channel and classification policy 
before retrieval or fan-out.
 MCP-BR-11: Coordination messages and events shall not contain preserved source code, diffs, secrets or 
credentials.
 MCP-BR-12: State that spans MCP calls is referenced by explicit project, campaign, channel, message and cursor 
identifiers; transport connections do not define business-session lifetime.\n\n===== PAGE 66 =====\n\nDEVWEAVE  |  SOFTWARE REQUIREMENTS SPECIFICATION

17.18 Normative conclusion
Each project shall have a logically project-scoped MCP service that enables authorized agents operating across

G.3 Illustrative real-time message flow
• Agent A authenticates to the project MCP service and calls devweave_coordination_send_message with projectId, 
campaignId, channelId, typed payload and idempotencyKey.
• The service validates the authenticated principal/runtime, project and channel permissions, message schema, 
payload size and source-code/secret policy.\n\n===== PAGE 68 =====\n\nDEVWEAVE  |  SOFTWARE REQUIREMENTS SPECIFICATION
Page 68 of 75
• The coordination domain service commits CoordinationMessage, channelSequence, CoordinationEvent and outbox 
record in a transaction. Only after commit does the tool return the messageId and sequence.
• The dispatcher publishes the committed event to the internal fan-out layer. Active subscriptions matching the 
channel resource receive a standard MCP resource-update notification on their subscriptions/listen stream.
• Agent B receives the notification as a wake-up signal and invokes resources/read or 
devweave_coordination_read_messages with its last processed cursor.
• The service reauthorizes the read and returns the ordered message/event page, current cursor and continuation 
cursor. Agent B deduplicates by messageId/eventId and optionally acknowledges its processed-through cursor.
• Agent B replies through the same project MCP service. The service persists the reply, signals subscribers and 
maintains the durable history.
• If Agent B was offline or the notification was missed, it reconnects and reads from its last cursor. The durable store, 
not the notification stream, provides completeness.

18. Business Vision, Commercial Model and Business-Aligned Requirements
This section translates the agreed business direction into product-level requirements. It is normative where 
requirements use SHALL/SHOULD/MAY. Market sizing, plan prices, revenue projections and channel assumptions are 
non-normative planning hypotheses and shall be maintained in separate, versioned business plans and commercial 
catalogues. This SRS defines what the product must support, not a guaranteed commercial outcome.
18.1 Commercial product positioning
DevWeave is positioned as an AI Software Delivery Control Plane: a hybrid, agent-neutral platform that connects 
approved software plans, distributed agent execution, codebase integration, verification evidence and persistent 
project knowledge. The product shall sell a delivery outcome—coordinated, governable and traceable software work—
not merely a document repository, coding model, agent chat interface or generic task board.
The principal product promise is: turn an approved software plan into coordinated work across multiple AI agents and 
execution environments, then preserve the decisions, activity, integration references and verification evidence needed 
to understand and trust the result.
18.2 Initial target customers and buying roles
The initial market-entry segment shall be AI-first software development agencies and development studios managing 
multiple client projects and using multiple AI coding agents. AI-native startups and independent development studios 
are secondary early segments. Mid-market software companies are a subsequent segment; large enterprises and 
platform-engineering organizations are later expansion segments after security, reliability, support and deployment 
requirements have been validated.
The economic buyer is generally an agency owner, CTO, engineering leader, head of delivery or platform engineering 
leader. Daily users include project owners, delivery managers, software engineers, agent/runtime operators, reviewers 
and AI agents. Agency clients may receive limited stakeholder access to their own projects. A purchaser, project owner, 
tenant administrator and client stakeholder are distinct roles and shall not be conflated.

18.3 Hybrid business and execution model
DevWeave shall support two execution modes through one common control plane. Customer-managed external 
execution is the initial commercial mode: customers connect agents and runtimes operating on their own devices, 
servers, cloud accounts or third-party platforms. DevWeave-managed execution is an optional later service: DevWeave 
provisions and operates isolated, short-lived execution workspaces/runners. A project or campaign may select one 
mode or combine both when the managed-execution release is available.\n\n===== PAGE 70 =====\n\nDEVWEAVE  |  SOFTWARE REQUIREMENTS SPECIFICATION
Page 70 of 75
The Knowledge Plane and Coordination/Control Plane shall be independent of the Execution Plane. Agent identity, 
project permissions, plan baseline, task ownership, communication history, evidence and integration governance shall 
not depend on whether a runtime is customer-managed or DevWeave-managed. Execution-provider adapters shall 
implement a stable, versioned runtime contract.
 Customer-managed execution: the customer controls the machine/runtime and normally pays its model, provider 
and compute charges directly. DevWeave provides coordination, authorization, context, status and evidence 
services.
 DevWeave-managed execution: DevWeave provisions isolated ephemeral workspaces and manages 
compute/runtime lifecycle. Usage shall be metered and exposed to the tenant. Managed runtime credentials and 
customer repository permissions shall be scoped and revocable.
 Hybrid campaigns: external and managed runtimes may participate in the same campaign and project MCP 
service, subject to identical plan-baseline, lease, workspace isolation, review and integration policies.
 Bring-your-own-key/provider: the product should support tenant-supplied provider credentials where permitted. 
Secrets shall be held in a protected credential store and shall not be exposed to agent messages, knowledge 
payloads or logs.
 The platform shall not require customers to use DevWeave-managed compute, a single model provider, a single 
coding agent or a single source-code host.
18.4 Commercial packaging and pricing principles
DevWeave shall support configurable commercial plans and entitlements without hard-coding public plan names, 
prices, currencies or limits into domain logic. The product may be offered through free/trial, team, studio/business and 
enterprise packages, but the actual catalogue is a commercial configuration. Prices and forecasts are not requirements 
and shall be maintained outside this SRS.
The recommended commercial structure is a platform subscription plus configurable coordination capacity and 
optional managed-execution consumption. Registered agent identity count shall not be the sole or default billing unit; 
metering should focus on meaningful resource or service consumption such as concurrent active runtime sessions, 
managed execution units/minutes, compute class, storage/retention and support/deployment tier. The exact billable 
dimensions remain a product/finance decision.

18.5 Product value proposition and measurable outcomes
The product shall make it possible to measure whether coordination, knowledge continuity and governance improve 
software-delivery operations. It shall not claim guaranteed productivity or quality improvements. Customer-specific 
baselines and measurement windows shall be agreed before making quantified ROI claims.
The recommended North Star product metric is Verified Coordinated Delivery Outcomes per Paying Workspace per 
Period: the number of execution campaigns reaching their declared success criteria with required integration and 
verification evidence, normalized by active paying workspace and reporting period. The metric shall be decomposable 
by project, campaign type, execution mode and customer segment, subject to permissions and privacy policy.

18.7 Commercial governance and non-functional considerations
 Commercial entitlements shall be evaluated by shared authorization/entitlement services; UI-only limits are 
insufficient.
 Usage metering shall be idempotent, auditable, reconcilable and resilient to delayed provider events. Metering 
shall not expose credentials, source code, private message bodies or unnecessary personal data.
 The control plane shall remain useful if a managed execution provider is unavailable. Customer-managed 
execution and knowledge retrieval shall not be disabled solely because an optional managed runtime provider is 
degraded.
 Managed execution shall use isolated tenant-aware resource pools, least-privilege credentials, network policy, 
resource quotas, image/version controls and cleanup verification.\n\n===== PAGE 74 =====\n\nDEVWEAVE  |  SOFTWARE REQUIREMENTS SPECIFICATION
Page 74 of 75
 Customer-managed and DevWeave-managed execution shall be distinguishable in reports, usage statements and 
audit records.
 The platform shall publish plan limits and managed execution rates before usage is incurred. Hard-limit, soft-limit 
and overage behavior shall be tenant-visible and configurable within product policy.
 Plan cancellation shall not immediately destroy tenant knowledge. Export, retention, legal hold, grace period and 
deletion shall follow documented tenant-exit policies.
18.8 Market, pricing and revenue assumptions outside the normative baseline
The initial go-to-market hypothesis is agency-first, followed by AI-native studios/startups, mid-market software 
companies and later enterprise platform-engineering teams. The hybrid commercial model is platform subscription 
plus configurable coordination capacity and optional managed-execution usage. The product should not require per-
registered-agent pricing; the commercial catalogue may use active concurrency, managed resource consumption, 
storage/retention, project/application entitlements and support/deployment tier as configurable dimensions.
No fixed price, free-tier limit, customer count, annual recurring revenue, gross margin, market share or break-even 
date is a normative SRS requirement. Such assumptions shall live in a separate financial model, be reviewed against 
customer evidence, and shall not be used as software acceptance criteria.
